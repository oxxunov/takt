# Такт — TUPIC GAMES

Ритм-игра в жанре падающих плиток без встроенной лицензированной музыки.
Игрок выбирает свой аудио- или видеофайл, приложение локально анализирует
звук и генерирует уровень.

## Принцип

Файл не покидает устройство. Декодирование и анализ идут через
`MediaExtractor` + `MediaCodec` и нативный анализатор, ничего не
загружается на сервер.

## Архитектура

Подробности — в ARCHITECTURE.md. Кратко: три модуля, `:app -> :engine -> :core`,
ядро без Android и потому под юнит-тестами.

## Слои

```
PcmDecoder      файл -> моно float PCM        (Kotlin, MediaCodec)
NativeAnalyzer  PCM -> онсеты + BPM + фаза    (C++ через JNI)
AnalysisCache   кэш результата анализа        (бинарный .rga)
BeatmapGenerator онсеты -> ноты по дорожкам   (Kotlin, мгновенно)
GameEngine      ноты + время -> оценки/счёт
GameView        отрисовка и ввод              (SurfaceView)
MusicPlayer     воспроизведение + часы        (AudioTrack.getTimestamp)
ClickEngine     звук попадания и метроном     (AAudio LOW_LATENCY)
```

Кэшируется **результат анализа**, а не готовая раскладка: анализ занимает
секунды, генерация раскладки — микросекунды. Смена сложности или ползунка
плотности пересобирает уровень мгновенно, без повторного разбора файла.

## Алгоритм анализа (`app/src/main/cpp/analyzer.cpp`)

1. Децимация до 22050 Гц, STFT окном 512 с шагом 128 (~5.8 мс).
2. Спектральный поток в лог-домене с полуволновым выпрямлением.
3. Адаптивный порог: скользящая медиана x 1.35.
4. Пик-пикинг с параболической интерполяцией вершины (субкадровая точность).
5. Локальный темп — автокорреляция в скользящих окнах по 8 с, медианное
   сглаживание, проверка октавной ошибки.
6. Отслеживание долей динамическим программированием: доля ставится туда, где
   сильный удар, а интервал штрафуется за отклонение от локального периода.

Единого темпа на весь трек НЕ используется. Живая музыка плывёт, и ошибка
в 0.2 BPM за четыре минуты уводит жёсткую сетку на сотни миллисекунд:
настоящие удары перестают попадать в допуск, а шум рядом с уехавшей сеткой,
наоборот, проходит. На тесте с темпом, плывущим со 124 до 129 BPM, старая
жёсткая сетка расходилась до 746 мс; отслеживание долей держит 8.5 мс
на всей длине.

Проверено на синтетических треках: BPM 127.95 при истине 128.0, recall
онсетов 100%, средняя ошибка тайминга 4.9 мс.

## Генерация раскладки

Три фильтрующих слоя, без них сырые онсеты дают неиграбельную кашу:

1. **Сетка** — узлы строятся между КАЖДОЙ парой соседних долей, поэтому
   подразделения следуют за живым темпом. Онсет, не попавший в узел
   с допуском, отбрасывается как артефакт.
2. **Порог силы и отсев хвостов** — удар вскоре после заметно более сильного
   почти всегда его затухание, а не новое событие в музыке.
3. **Квота плотности** — скользящее окно 2 с, квота масштабируется по
   локальной энергии, поэтому припев плотнее куплета.
4. **Дорожки** — по спектральному центроиду и басовости, через перцентили.
   Мелодия рисуется по экрану, дорожки заполняются равномерно.

## Калибровка

Обязательный шаг. Выходная задержка на Android гуляет от 40 до 200+ мс.
Метроном щёлкает через AAudio, момент реального воспроизведения берётся из
таймштампа потока, игрок стучит в такт, считается медиана расхождения.

## Сборка

CI собирает debug APK на каждый push. Локально:

```
gradle assembleDebug
```

Тесты ядра:

```
gradle :core:test
```

Gradle-обёртки в репозитории нет, её ставит экшен `gradle/actions/setup-gradle`.

## Что не сделано

- Длинные ноты (удержания)
- Видеорежим — под него оставлен интерфейс `GameClock`
- Реактивный фон по FFT
- Режим практики и No-Fail
- Сегментация трека по self-similarity
